## Recorded live results

The development machine's Wallpaper Engine configuration reports a global
Scene limit of **25 FPS**. The controller requested 60 FPS and reported this
source limit instead of claiming 60 FPS or fabricating frames.

| Case | Backend | Result |
|---|---|---|
| Saki / Lofi Girl / Makima switch cycle 1 | WGC + hardware H.264 + WebCodecs | 36 / 37 / 23 presented during the short sampling windows; zero decode errors |
| Saki / Lofi Girl / Makima switch cycle 2 | WGC + hardware H.264 + WebCodecs | 26 / 43 / 27 presented; zero decode errors |
| Lofi Girl detailed run | Same | 93 received and 93 presented, zero dropped and zero decode errors, no transport error |
| Lofi Girl repeat after batching stabilization | Same | 104 received and 104 presented, zero decode errors |

One direct Lofi capture/encode sample produced about 122 captured and 118
encoded frames in roughly 6.1 seconds. Capture wait consumed about 4.87 seconds
and encoding about 0.86 seconds, showing that the current 25 FPS source/capture
cadence—not hardware H.264 throughput—was the immediate limit in that run.

## Gates not yet passed

- The 1920×1080 true-source 60 FPS, 10-minute, ≥55 presented FPS gate was not
  run because Wallpaper Engine is currently set to 25 FPS. The user must change
  Wallpaper Engine's own Performance FPS setting to 60 before this test is
  meaningful; the controller does not alter that global preference.
- The current Codex CSP blocks the planned loopback media connection. H.264
  frames therefore use bounded Base64 batches over CDP. This is materially
  better than per-frame JPEG/CDP but does not satisfy the strict transport gate.
- The encoder currently receives CPU NV12 buffers after a D3D11 readback; full
  GPU texture-to-encoder zero-copy remains future work.
- The full 50-switch/5-project test, per-case 10-minute soak, deterministic
  fault-injection matrix, median/p95 encode-to-present latency, and formal
  process CPU/GPU/memory sampling remain pending.

## Current product judgment

The implementation demonstrates a stable hardware H.264/WebCodecs route and
fixes important ownership and stale-session failure modes, but it must remain
an explicitly labeled test build until the outstanding hard gates are measured
and the transport constraint is resolved or the shared specification is
consciously revised during product convergence.

## Maintainer visual check — 2026-09-21

The maintainer confirmed that connection and Apply succeeded without an error,
the new path was visibly smoother and substantially more stable than v0.3, and
the sampled wallpapers showed no black/gray flash, disappearance, frozen frame,
old-wallpaper recurrence, tearing, color block or color corruption. Repeated
manual switching did not reproduce the earlier deadlock. The private render
window was absent from both the taskbar and Alt+Tab.

Two follow-up defects were recorded:

- Closing the adjustment process froze a Scene on its last frame because that
  process owned capture and encoding. v0.4.1 now treats the window close button
  as “hide to notification area”; the stream stays live until the explicit
  Restore-and-exit command.
- Independent width/height caps could alter the capture aspect ratio on high
  DPI or wide viewports, after which `Cover` cropped additional edges. v0.4.1
  preserves the viewport ratio, raises the clarity ceiling to 2560×1600 and
  increases the local H.264 bitrate.

Wallpaper Engine itself produced one `KERNELBASE.dll`/`0xE06D7363` crash dump
during the manual session and restarted afterward. This is recorded as an open
upstream/runtime stability observation, not falsely marked fixed. The bounded
session monitor is expected to keep the last frame and attempt recovery, but a
longer repeated-switch run is required to determine whether the crash recurs.

## v0.4.2 persistence, fit and color follow-up

- Added a headless-persistence tray command. It keeps live playback active,
  hides the tray icon, enables the per-user sign-in worker and remembers the
  last wallpaper. Relaunching the same executable reopens the existing UI.
- Added an explicit “show complete wallpaper” control. It selects `Contain` and
  centers the image. This is the only geometrically correct way to show every
  edge when the wallpaper and Codex viewport have different aspect ratios;
  filling the whole viewport must otherwise crop or distort.
- Made the existing 0.25×–2.00× Scene/video playback speed control more visible
  and added a one-click 1.00× reset.
- Changed HD capture color conversion from BT.601 to limited-range BT.709 and
  added explicit Media Foundation color metadata. Synthetic hardware H.264
  encoding and all 26 self-tests pass after this change.

## v0.4.3 Codex-restart persistence and visual-quality follow-up

- Added an opt-in, separately named desktop launcher that starts Codex with its
  startup-only local wallpaper channel and restores the remembered wallpaper
  without first showing the adjustment window. It never replaces the official
  Codex shortcut. If an unchannelled Codex is already open, it offers only a
  confirmed normal close/reopen and never force-terminates the process.
- Added a brighter high-clarity preset that uses full Scene scale, removes the
  media veil and blur, reduces panel dimming, and applies mild adjustable
  brightness/contrast/saturation compensation.
- Raised the local H.264 quality budget to 8–40 Mbit/s. This reduces compression
  loss but does not claim pixel equivalence with Wallpaper Engine's direct
  desktop compositor; the current stream remains NV12/H.264 4:2:0.

## v0.4.4 catalog, native-video and controller follow-up

- Removed the v0.4.3 desktop launcher after field testing showed that it could
  not reliably attach the startup-only channel to every later Codex launch.
  The controller now removes only its own exact legacy shortcut and leaves the
  official Codex shortcut untouched.
- Made tray Restore-and-exit idempotent. A missing CDP listener now means the
  page has already gone away; it no longer blocks release of capture, encoder,
  private Wallpaper Engine window, and controller resources.
- The brighter high-clarity action now reconnects and applies immediately when
  possible, otherwise reports that the values are saved for the next Apply.
  **Preset settings…** persists user-defined one-click values, while the normal
  controls remain editable after application.
- Official Workshop scans now use only IDs found in both Steam's current item
  details and installed-item sections. A successful rescan replaces Wallpaper
  Engine entries (preserving personalization), removes stale unsubscribed
  projects, and does not touch local entries. Manifest failure leaves the old
  catalog intact.
- Validated Wallpaper Engine videos above the 256 MiB direct-upload ceiling use
  official `playInWindow` playback and the existing WGC/hardware-H.264 pipeline.
  The 362 MiB `蕾塞 1226` project therefore avoids browser Blob/Base64 copies.
- The v0.4.3 desktop-launcher bullets above remain as historical notes only;
  they are superseded by this v0.4.4 decision.

## v0.4.5 named presets and compact-window layout follow-up

- The v0.4.4 single preset is imported without losing its values. The selected

## v0.4.6 manual startup and bilingual-interface follow-up

- Removed **Restart Codex normally and apply now**, its confirmation dialog,
  and the normal-close service. The controller no longer asks Windows to close
  or restart an active Codex task.
- When Codex is already open without the startup-only wallpaper channel, the
  selected wallpaper is remembered and the user is told to close Codex
  manually, then choose **Start / reconnect Codex**. No deferred close waiter
  is launched by the interactive Apply or Connect paths.
- Kept the main **Restore Codex background** action unchanged. The tray exit is
  now **Remove wallpaper and exit**: it makes one cleanup attempt capped at two
  seconds, skips page cleanup immediately when another operation is still
  stopping, and exits even when Codex is closed or unavailable.
- Added an English/Chinese switch beside the connection controls. The selected
  language is stored in the existing backward-compatible state schema and is
  applied to the main controls, dialogs, tooltips, filters, and tray menu.

## v0.4.7 startup and renderer-target recovery follow-up

- Connection now prefers the normal `app://-/index.html` Codex shell and does
  not inject into auxiliary avatar-overlay or detached-window targets when the
  normal shell is available. Those auxiliary pages share theme variables with
  the shell and could previously pass the visual probe while keeping the actual
  wallpaper invisible.
- A new connection must keep the same verified main target and native surface
  across a short stability window before it is reported as ready. Apply also
  revalidates the target and reconnects automatically when an apparently open
  WebSocket belongs to a replaced renderer.
- Local CDP discovery allows eight seconds per bounded request, while first
  startup polling tolerates a busy Windows sign-in for longer. This removes the
  former three-second false timeout without permitting remote endpoints or
  unverified listener processes.
- Automatic and button-triggered remembered-wallpaper restores now enter the
  same first-frame and live-stream monitoring path as **Apply selected**.

## v0.6.0 silent-stream recovery baseline

- Added a presentation watchdog to the existing bounded connection monitor.
  It distinguishes capture, hardware-encoder, local-transport and Codex
  presenter stalls using privacy-safe counters and timestamps.
- Intentional hidden-window pause and the first-frame warm-up window are
  excluded from recovery. A real stall reuses the existing last-good-frame
  behavior and the shared maximum of two recovery attempts; Codex is never
  closed or force-terminated.
- Added deterministic self-tests for healthy, warming, hidden, capture,
  encoder, transport and presenter states plus the recovery-attempt ceiling.

## v0.6.1 upgrade and watchdog-diagnostics follow-up

- Doctor now reports whether it is attached to the live controller, the current
  watchdog health class, presentation and native-pipeline counters, recovery
  count, and the latest recovery kind/time. The selected wallpaper's absolute
  path is not serialized, and probe failures expose only an exception type.
- Added a guarded cross-version installer test. It refuses to run over a live
  controller or an existing registered installation, installs the previous
  stable version into an isolated temporary directory, upgrades it in place,
  verifies executable and registry versions, runs both installed self-tests,
  performs a silent uninstall, and verifies that existing `state.json` and
  `library.json` hashes never change.
- The on-demand Windows release-candidate workflow now checks out `main` as the
  stable baseline and runs that stable-to-candidate path whenever the candidate
  version is newer. Codex is never closed or force-terminated.

## v0.7.0 timestamp-paced 60 FPS and clarity candidate

- Replaced burst presentation of decoded H.264 batches with an eight-frame
  bounded timestamp queue driven by `requestAnimationFrame`. When behind, the
  browser closes older due frames instead of accumulating latency.
- Shortened and bounded CDP coalescing for 60 FPS, raised the local hardware
  encode ceiling from 40 to 60 Mbps, and reused the NV12 conversion buffer to
  avoid one multi-megabyte managed allocation per captured frame.
- Encoder timestamps stay monotonic when a live frame-rate change recreates the
  Media Foundation transform. Doctor now reports measured capture, encode and
  presentation FPS, dimensions, average stage times, target bitrate, transport
  rate, publisher batches and decoder queue depth.
- Static/runtime tests cover the pacing markers, bounded queue, bitrate policy
  and derived performance metrics. Real 60 FPS visual/soak acceptance remains
  a maintainer test because it depends on the installed GPU, driver, Codex and
  Wallpaper Engine configuration.

## v0.7.1 real-capture-clock experiment

- Real hardware evidence showed that tying presentation to captured timestamps
  was not portable across Wallpaper Engine projects. Two samples presented only
  17/338 and 1/713 received frames even though WebCodecs reported no errors.
- The experiment is retained in its historical branch but removed from the next
  candidate rather than adding project-specific timing exceptions.

## v0.7.2 refresh-paced presenter candidate

- Decoded CDP batches are drained at one frame per browser display refresh. The
  presenter no longer waits on source timestamps, so unusual scene clocks cannot
  stall an otherwise valid decoded stream.
- The eight-frame bound still prevents unbounded latency. Only actual queue
  overflow discards frames.
- Doctor now reports the presentation queue separately from the WebCodecs decode
  queue and labels severe sustained loss as `PerformanceDegraded` instead of the
  misleading `Healthy` state.

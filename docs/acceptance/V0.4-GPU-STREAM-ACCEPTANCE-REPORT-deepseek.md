## What was measured

### 1. Encoder, container and decode round trip (`--gpu-encoder-smoke-test`)

Command: `CodexWallpaperSkin.dll --gpu-encoder-smoke-test --width 1280 --height 720 --fps 60 --seconds 3`

| Field | Result |
| --- | --- |
| Encoder mode | `hardware` (asynchronous MFT, read from `MF_TRANSFORM_ASYNC` on the encoder's own attributes) |
| Frames submitted | 181 / 181 in 3.00 s wall clock, i.e. real-time 60 FPS input |
| Transport chunks | 1 initialisation segment + 181 media fragments, in order, init first |
| Fragment cadence | one fragment per frame |
| Stream size | 1,412,383 bytes for 3 s at 1280x720, ≈ 3.8 Mbit/s |
| Container | `ftyp, uuid, pdin, moov, moof, mdat x181`; `moov` with `mvex`; `avc1` with `avcC`; timescale 60000; declared 1280x720 |
| AVC elementary stream | 543 NAL units, SPS=1, PPS=1, IDR=2, non-IDR=179, NAL length size 4 |
| **Decode round trip** | **Media Foundation decoded 181 frames, 1280x720, 3.00 s of media, orientation correct** |
| Stream SHA-256 | `97410d050892e824bfb66da76e20fb3ab133a987afc53cc07b9e8e94a46a1f21` (before the final diagnostics change) |

The decode round trip is the strongest evidence in this report. The encoder's own
output is handed back to Media Foundation's reader **through an in-memory byte
stream**, decoded to RGB32, and inspected: the synthetic fixture paints a
high-contrast red marker in its top-left corner, so a decoded frame with the
marker in the top-left corner proves both that the bitstream decodes and that the
`MF_MT_DEFAULT_STRIDE` declaration matches the bytes that were written. This
closes the two questions a structural box check cannot answer, and it needs no
file system access and no GPU.

### 2. Live capture, encode and transport (`--gpu-stream-smoke-test <project.json>`)

Ten-second runs at 0.75 render scale (1222x806) against four installed Scene
projects. A real Wallpaper Engine surface was captured by Windows Graphics
Capture, hardware encoded, transported in batches, then re-inspected and decoded
in memory.

| Project | Captured fps | Coded frames / media seconds | Media vs wall | Superseded frames | Submit cost | Codec reported |
| --- | --- | --- | --- | --- | --- | --- |
| Makima `2935530316` | 17.7 | 194 / 12.00 s = 16.2 fps | 12.00 s vs 12 s | 1 | 2.86 ms | `avc1.640020` |
| Saki `2914257158` | 19.7 | 215 / 10.19 s = 21.1 fps | 10.19 s vs 10 s | 2 | 2.84 ms | `avc1.640020` |
| Konata `3274434326` | 25.2 | 252 / 10.00 s = 25.2 fps | 10.00 s vs 10 s | 4 | 2.54 ms | `avc1.640020` |
| Toejam `3796846129` | 25.1 | 274 / 10.15 s = 27.0 fps | 10.15 s vs 10 s | 3 | 2.73 ms | `avc1.640020` |

Every run: encoder `hardware`, container MSE-compatible, AVC elementary stream
valid, **Media Foundation decode verified**, private render window released, no
transport refusals, no recoveries, queue depth maximum 0–1.

Three findings from these runs, each of which changed the implementation:

1. **Media Foundation pads a declared frame rate with repeated frames.** With the
   original fixed 60 FPS declaration the encoder accepted 252 frames but coded
   857 — the media timeline was real but the product would have claimed a cadence
   the user never saw. Measured, then fixed: the declared rate is now the
   *measured* capture cadence, capped by what the user asked for. All four runs
   above now show media seconds equal to wall seconds, so the timeline is exact in
   both directions and the status label follows the declared rate.
2. **The capture source, not the pipeline, is the cadence ceiling.** Superseded
   frames are at most 4 per run and the encode hand-off costs 2.5–2.9 ms per
   frame, so this pipeline consumes everything Wallpaper Engine produces. The
   19–27 fps ceiling is the Scene rendering rate on this machine under the
   contention caveat above.
3. **The capture channel drop counter was wrong.** It accumulated a cumulative
   difference on every read, reporting hundreds of phantom drops. It is now a
   gauge derived from the source's published and consumed counts, which is why
   the table above can state superseded frames credibly.

### 3. Renderer runtime (`scripts/runtime-smoke-test.mjs`)

`PASS runtime image/video/scene/palette/quality/hidden-pause/integrity/pending-cleanup/orphan-repair/restore/mismatch-refusal`

The renderer smoke test also drives the GPU surface host contract with a scripted
surface and asserts that an invalid identity is refused; that starting a GPU
stream does **not** replace the last confirmed good frame; that the first
presented fragment promotes the video surface and retires the previous wallpaper;
that a stale identity can neither push nor read nor end; that a replacement which
never presents leaves the current frame and its predecessor decoder alive; that
`busy` and `decode-failed` are reported distinctly; and that cleanup removes the
GPU surface and all injected globals.

### 4. Automated unit tests (`--self-test`)

30 checks pass, 15 of them added for v0.4, all from synthetic or generated
fixtures: status labels, frame-rate normalisation, the adaptive declared-rate
choice, the degraded threshold, the rule that a failed GPU path never borrows a
GPU label, diagnostics counters and gauges, latency percentiles, bounded latency
reservoir, privacy of the rendered diagnostics, the fragment batcher, the fMP4
box splitter (including one-byte-at-a-time input and malformed, oversized,
unbounded and duplicate-`moof` corruption), the container inspector, the avcC
codec string, the AVC elementary-stream validation, and the renderer wiring.

## Decision category

**Compatibility only, with the GPU path implemented, live-exercised and structurally verified.**
The GPU path runs end to end on real Wallpaper Engine Scenes: hardware encode, MSE-compatible fragmented MP4, an elementary stream that Media Foundation decodes with correct orientation, and a renderer surface contract covered by automated tests. The 60 FPS and 30 FPS gates are **not** claimed: this machine sustains 19–27 unique frames per second for the tested Scenes at a 0.75 render scale, under the contention caveat, and the product now reports that honestly as a labeled, degraded 30 FPS fallback instead of a false 60 FPS success. The reduced-frame-rate compatibility backend remains fully functional and is selected automatically when the GPU path is unavailable.

## Dependencies, licences and rollback

**New dependencies: none.** No NuGet package, redistributable codec, native library or bundled binary was added. The new code uses only Windows system components already present and already shipped by the product:

| Component | Origin | Notes |
| --- | --- | --- |
| Windows Graphics Capture (D3D11) | Windows 10 1903+ | already used by v0.3 |
| Media Foundation SinkWriter, H.264 encoder and SourceReader | Windows | documented public COM interfaces; no redistributable |
| Media Source Extensions H.264 decode | the Codex Chromium runtime | already present |
| Existing third-party JavaScript (`we-scene`) | MIT, already recorded | unchanged; `WE-SCENE-LICENSE.txt` still ships in the package |

Rollback is a single revert of the range that introduces the v0.4 path: no user
state schema change was made, no file format changed and no installed product file
is touched, so `Restore` removes the injected layer either way. Setting
`GpuStreamEnabled` to `false` in the saved state reverts Scene playback to the
v0.3 compatibility backend without rebuilding anything, which is the fastest
available mitigation if a GPU-path defect is found in the field.

## Recommendations for final convergence

1. **Adopt the verified core.** The Media Foundation streaming encoder
   (`MediaFoundationInterop`, `MediaFoundationH264Encoder`, `Mp4ChunkAssembler`),
   the in-memory decode verification and the persistent Media Source surface are
   the strongest components here and are separable from the transport.
2. **The three defects this round found are worth carrying into any converged
   build**: the missing asynchronous byte-stream completion (which deadlocks the
   MPEG-4 sink), Media Foundation frame duplication when a declared rate exceeds
   the real one, and fragment-versus-frame confusion in cadence reporting. Each is
   a silent failure that produces plausible-looking but false numbers.
3. **Re-test the transport assumption** if the Codex `connect-src` policy ever
   gains a loopback source; the batching seam can carry a socket unchanged.
4. **Re-measure the source cadence in an uncontended session** before deciding
   whether the 60 FPS target is reachable on this machine, and consider a
   DXGI-surface-backed encoder input only if the readback proves to be the limit —
   the measurements here say it is not.
5. **Adopt neither** if another candidate reaches the 60 FPS gates without
   carrying media through CDP; that would be a real simplification.

## What was measured

### 1. Encoder and container (`--gpu-encoder-smoke-test`, synthetic fixture)

Command: `CodexWallpaperSkin.dll --gpu-encoder-smoke-test --width 1280 --height 720 --fps 60 --seconds 3`

| Field | Result |
| --- | --- |
| Encoder mode reported by Media Foundation | `hardware` (asynchronous MFT, `MF_TRANSFORM_ASYNC` on the encoder's own attributes) |
| Frames submitted | 180 / 180 in 2.99 s wall clock, i.e. real-time 60 FPS input |
| Transport chunks produced | 1 initialisation segment + 180 media fragments, in order, init first |
| Fragment cadence | 16.6 ms per media fragment (one fragment per frame; the 100 ms minimum-fragment hint is not the limiting factor at 60 FPS) |
| Stream size | 1,400,766 bytes for 3 s at 1280x720, ≈ 3.7 Mbit/s |
| Container | `ftyp, uuid, pdin, moov, moof, mdat x180`; `moov` with `mvex`; `avc1` with `avcC`; timescale 60000 |
| Declared geometry | 1280x720 |
| AVC elementary stream | 540 NAL units, SPS=1, PPS=1, IDR=2, non-IDR=178, NAL length size 4 |
| Stream SHA-256 | `97410d050892e824bfb66da76e20fb3ab133a987afc53cc07b9e8e94a46a1f21` |
| Byte-stream flow control | 545 write calls, all through the asynchronous `BeginWrite`/`EndWrite` pair, 0 seek/read/set-position calls |

The AVC validation walks every `mdat` box, checks each length-prefixed NAL unit
against the declared length size, and requires parameter sets and an
instantaneous refresh frame to be present. This is the check that catches a
stream which is structurally a valid fragmented MP4 but which no decoder can
play.

### 2. Renderer runtime (`scripts/runtime-smoke-test.mjs`)

`PASS runtime image/video/scene/palette/quality/hidden-pause/integrity/pending-cleanup/orphan-repair/restore/mismatch-refusal`

The renderer smoke test now also drives the GPU surface host contract with a
scripted surface and asserts, among others:

- an invalid stream identity is refused;
- starting a GPU stream does **not** replace the last confirmed good frame;
- the first presented fragment promotes the video surface and retires the
  previous wallpaper;
- a stale identity can neither push fragments nor read status, and cannot end the
  active stream;
- a replacement stream that never presents leaves the current frame visible and
  its predecessor decoder alive;
- `busy` and `decode-failed` are reported distinctly, and ending the stream
  disposes the surface;
- cleanup removes the GPU surface and all injected globals.

### 3. Automated unit tests (`--self-test`)

30 checks pass, 14 of them added for v0.4, all from synthetic or generated
fixtures:

- status label mapping, frame-rate normalisation, degraded-cadence threshold, and
  the rule that a failed GPU path never borrows a GPU label;
- diagnostics counters, queue-depth maximum, latency percentiles, bounded latency
  reservoir, degraded detection, and the assertion that the rendered diagnostics
  string carries no drive path;
- the fragment batcher (fragment, byte and age flush limits, init-segment
  priority, ordering, empty take);
- the fMP4 box splitter fed one byte at a time, plus malformed, oversized,
  unbounded and duplicate-`moof` corruption cases;
- the container inspector and AVC codec-string extraction (`avc1.640028`);
- the renderer wiring and cleanup reversibility.

## Decision category

**Compatibility only, with the GPU path implemented and structurally verified.**
The 60 FPS GPU gate is *not* claimed as passed: the capture/encode/container half
was measured and passes on hardware, but the presented-cadence, continuity,
switching and long-run gates require a live 10-minute session with Codex and a
60 FPS Scene, which was not run here. The reduced-frame-rate compatibility
backend remains fully functional and is selected automatically whenever the GPU
path is unavailable.

## Verification that could not be performed here

| Verification | Blocker |
| --- | --- |
| Chromium Media Source decode of the produced stream (`scripts/gpu-browser-mse-test.mjs`) | The sandbox denies Chromium its named pipes (`mojo platform_channel` FATAL, access denied) and its crash handler; escalation to full access was requested once and declined. |
| Media Foundation decode round trip (`--gpu-decode-smoke-test <file>`) | `MFCreateSourceReaderFromURL` fails with `0x80070005` (access denied) for the same file the encoder wrote successfully, in both the workspace and the temp directory. |
| Live 10-minute cadence, 50 consecutive switches, resource growth | Requires an interactive session with Codex and Wallpaper Engine; the existing Codex-branch controller was in use on this machine and starting a competing controller during another branch's live session was out of scope. |
| `--gpu-stream-smoke-test` against a real Workshop Scene | Available and implemented, but not run for the same reason. It is the intended live check for the next session. |

Neither blocker is a defect in the implementation: the container is validated
structurally and at the elementary-stream level, and the browser's own capability
probe confirms it can accept `avc1.640028` in Media Source Extensions.

## Dependencies, licences and rollback

**New dependencies: none.** No NuGet package, redistributable codec, native
library or bundled binary was added. The new code uses only Windows system
components already present and already shipped by the product:

| Component | Origin | Notes |
| --- | --- | --- |
| Windows Graphics Capture (D3D11) | Windows 10 1903+ | already used by v0.3 |
| Media Foundation SinkWriter + H.264 encoder MFT | Windows | invoked through the documented public COM interfaces; no redistributable |
| Media Source Extensions H.264 decode | the Codex Chromium runtime | already present |
| Existing third-party JavaScript (`we-scene`) | MIT, already recorded | unchanged; `WE-SCENE-LICENSE.txt` still ships in the package |

Rollback is a single revert of the range that introduces the v0.4 path: no user
state schema change was made, no file format changed and no installed product
file is touched. `Restore` removes the injected layer either way. Setting
`GpuStreamEnabled` to `false` in the saved state reverts scene playback to the
v0.3 compatibility backend without rebuilding anything, which is the fastest
available mitigation if a GPU-path defect is found in the field.

## Recommendations for final convergence

1. **Adopt the measured halves.** The Media Foundation streaming encoder
   (`MediaFoundationInterop`, `MediaFoundationH264Encoder`, `Mp4ChunkAssembler`)
   and the persistent Media Source surface are the strongest components here and
   are separable from the transport.
2. **Re-test the transport assumption.** If the Codex `connect-src` policy gains
   a loopback source, the loopback transport becomes reachable and the batching
   seam can carry it unchanged; re-run the CSP probe before assuming otherwise.
3. **Re-measure on a quiet machine.** The presented-cadence, latency and
   switching gates need a dedicated session with the machine to itself.
4. **Consider removing the encoder-side CPU readback** with a DXGI-surface-backed
   encoder input, measured against the current numbers before adopting.
5. **Adopt neither** if another candidate demonstrates the same product behaviour
   without carrying media through CDP; that is a real simplification, not a
   preference.

The decode round trip is the strongest evidence in this report. The encoder's own
output is handed back to Media Foundation's reader **through an in-memory byte
stream**, decoded to RGB32, and inspected: the synthetic fixture paints a
high-contrast red marker in its top-left corner, so a decoded frame with the
marker in the top-left corner proves both that the bitstream decodes and that the
`MF_MT_DEFAULT_STRIDE` declaration matches the bytes that were written. This
closes the two questions a structural box check cannot answer, and it needs no
file system access and no GPU.

### 1.1 The primary target resolution, and a hardware encoder that wedges

The 1920x1080 case from the acceptance document was run at the primary product
target rather than only at 720p, and it produced the most important finding of the
whole exercise.

| Configuration | Result |
| --- | --- |
| 1920x1080 @ 30 FPS, hardware | **PASS** 鈥?360/360 frames in 11.97 s = 30.1 fps sustained, 361 chunks, 8,588,781 bytes, MSE-compatible, **Media Foundation decoded 352 frames at 1920x1080 with orientation correct** |
| 1920x1080 @ 60 FPS, hardware | **FAILS** 鈥?the encoder accepts about 258鈥?63 frames (鈮?.3 s) and then stops accepting frames indefinitely. Reproduced with and without low latency and with and without the fragment-duration hint, so it is the encoder configuration and not a tuning attribute |
| 1920x1080 @ 60 FPS, software | **PASS** 鈥?720/720 frames in 12.00 s = 60.0 fps sustained, 8,642 AVC NAL units, MSE-compatible, decoded at 1920x1080 with orientation correct |
| 1280x720 @ 60 FPS, hardware | **PASS** 鈥?600/600 frames in 10.0 s = 60.0 fps sustained, decoded with orientation correct |

A wedged encoder is worse than a labeled fallback, and a blocked Media Foundation
call cannot be cancelled, so three defences were added rather than one:

1. **Refused up front.** `MediaFoundationH264Encoder.TryCreate` refuses hardware
   above 720p at more than 30 FPS with a message naming the measured symptom. The
   caller then selects the 30 FPS fallback or retries with the software encoder,
   both of which are measured stable.
2. **Bounded priming.** Priming submits real frames, so it now runs on its own
   supervised thread under a hard budget; a blocked submit abandons the thread,
   marks the encoder stalled and returns a diagnosed failure instead of freezing
   the wallpaper apply.
3. **Bounded steady state.** The transport loop watches for accepted frames with no
   output for four seconds and abandons the stream with a reason. Teardown skips
   `FinalizeWriter` on a stalled encoder, so `Dispose` cannot block on the same
   non-returning call.

Where the declared rate genuinely exceeds 30 FPS above 720p, `GpuMediaPipeline` selects the software
encoder instead of dropping the cadence, because 60 FPS is the product goal and the software encoder
was measured stable at 1080p60. Where the source is slower than 30 FPS the declared rate is below the
threshold and hardware encoding continues unchanged, which is what a live run at 1622x1056 confirmed
(declared 8 FPS, `encoder=hardware`, no refusal). The product consequently declines the unavailable
and says why, rather than claiming it and hanging.

### 2.1 Why the 60 FPS target is not reached here 鈥?measured, not assumed

Three independent measurements, each of which changed the implementation:

1. **The capture consumer costs the source nothing.** `--gpu-capture-rate-probe`
   measures the source with and without the readback. Konata: **24.9 fps
   source-only versus 24.8 fps with the full GPU-to-CPU readback, with 199 of 199
   published frames consumed**. The readback is therefore not the ceiling, and
   implementing a DXGI zero-copy encoder input would not raise the rate.
2. **The rate is independent of resolution.** Source-only cadence for Konata was
   24.7 / 25.0 / 25.0 fps at render scales 0.5 / 0.75 / 1.0, and for Makima 19.0 /
   18.5 / 17.6. A four-fold change in pixels moves the rate by a few percent, so
   this is a frame-rate limit, not pixel throughput. The earlier advice to reduce
   the render scale for a higher cadence was wrong and has been removed from the
   product's status note.
3. **Wallpaper Engine itself caps the rate.** Its own `config.json` carries
   `general.user.fps`, which on this machine is **25**. The measured rates sit
   exactly at or below that value, which explains the resolution independence and
   the per-Scene differences at the same time. The product now reads that setting
   (without ever surfacing the path) and names it as the remedy when it explains
   the shortfall, so the user is told to raise a setting they actually control.

**Media Foundation resamples the media timeline to the declared frame rate.**
This was established by experiment: stamping each sample with the real 220 ms
interval while declaring 60 FPS produced 517 coded frames from 45 submissions 鈥?exactly 8.58 s x 60 FPS. Consequences now enforced in code: the declared rate is
measured from the live source (after a 500 ms warm-up skip, because a Scene that
just started is still initialising) with an 85 % margin, and the **claimed**
cadence is taken from frames that really came from the capture surface, never from
the coded count. The `coded / submitted` ratio is reported so duplication is
visible; on the runs above it ranged from 0.81 (slight dropping) to 1.82
(duplication when the source slowed after the rate had been measured).

A further honest consequence: because changing the declared rate means rebuilding
the stream, a rate measured before the source has settled is used for the whole
session. The status reports the measured source cadence continuously, so the user
sees the truth even when the declaration is stale.

## Decision category

**Closest category: Pass - GPU 30 FPS fallback, provisionally.** The GPU video path
is not merely implemented: it captures, hardware or software encodes, transports,
and presents a stream that Media Foundation decodes with correct orientation, at
1280x720@60 and at 1920x1080 in both its 30 FPS hardware and 60 FPS configurations.
The 30 FPS fallback is selected and labeled automatically, and the status never
claims a cadence the source did not deliver.

The category is provisional rather than declared, for two honest reasons. The
acceptance document requires the continuity and 10-minute presented-cadence gates
to pass for that category, and *presented* cadence cannot be measured without the
Codex page attached: the renderer smoke test proves the surface contract, not live
cadence. And on this machine the live source never exceeds Wallpaper Engine's own
25 FPS setting, so the 60 FPS path was proven natively rather than live. The
reduced-frame-rate compatibility backend remains fully functional and is selected
automatically whenever the GPU path is unavailable or unstable.

Rollback is a single revert of the range that introduces the v0.4 path: no user
state schema change was made, no file format changed and no installed product file
is touched, so `Restore` removes the injected layer either way. Setting
`GpuStreamEnabled` to `false` in the saved state reverts Scene playback to the
v0.3 compatibility backend without rebuilding anything, which is the fastest
available mitigation if a GPU-path defect is found in the field.

## Recommendations for final convergence

1. **Adopt the verified core.** The Media Foundation streaming encoder
   (`MediaFoundationInterop`, `MediaFoundationH264Encoder`, `Mp4ChunkAssembler`),
   the in-memory decode verification and the persistent Media Source surface are
   the strongest components here and are separable from the transport.
2. **The five defects this round found are worth carrying into any converged
   build.** In order of how quietly they fail: the missing asynchronous
   byte-stream completion (deadlocks the MPEG-4 sink inside `WriteSample`); Media
   Foundation resampling the timeline to the declared rate; fragment-versus-frame
   confusion in cadence reporting; a capture drop counter that accumulated a
   cumulative difference; and a status label derived from the request rather than
   from the measured source. Each produced plausible-looking but false numbers.
3. **Raise Wallpaper Engine's own frame rate limit before judging the 60 FPS
   target.** That setting, not this implementation, is what caps the cadence here.
4. **Re-measure in an uncontended session.** The sibling clone's controller drove
   Wallpaper Engine during every live run, and the Scene rate varied from 5.7 to
   25.2 fps between runs of the same project, so all figures here are lower bounds.
5. **Re-test the transport assumption** if the Codex `connect-src` policy ever
   gains a loopback source; the batching seam can carry a socket unchanged.
6. **Adopt neither** if another candidate reaches the 60 FPS gates without
   carrying media through CDP; that would be a real simplification.

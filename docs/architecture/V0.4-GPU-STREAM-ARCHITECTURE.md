# v0.4 GPU video stream — architecture (DeepSeek candidate)

Implemented on `deepseek/v0.4-gpu-stream`. This note describes capture, encoder,
transport, decoder/presenter, session ownership, fallback and cleanup as they are
actually built, not as they were originally sketched. The transport decision and
the evidence behind it are recorded in `docs/ARCHITECTURE_DECISIONS.md` (ADR-007).

## 1. Shape of the path

```
Wallpaper Engine playInWindow HWND
        |  Windows Graphics Capture (D3D11, free-threaded frame pool)
        v
staging texture -> tightly packed top-down BGRA byte[]
        |  quality gate (reject empty / uniform / undersized frames)
        v
Media Foundation SinkWriter
        |  MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS, RGB32 in, H.264 High out
        |  MF_TRANSCODE_CONTAINERTYPE = MFTranscodeContainerType_FMPEG4
        |  MF_MPEG4SINK_MOOV_BEFORE_MDAT, MF_LOW_LATENCY
        v
managed IMFByteStream -> MP4 box splitter -> moof+mdat fragments
        |  bounded batcher (4 fragments / 384 KiB / 60 ms, whichever first)
        v
existing authenticated CDP session -> injected renderer
        v
persistent <video> + MediaSource (hardware H.264 decode) inside Codex
```

## 2. Capture (native, `WindowsGraphicsCaptureSource`)

The existing Windows Graphics Capture source gained a second frame shape. The
compatibility backend still publishes a frozen `BitmapSource` so frames can be
JPEG encoded; the GPU path publishes the raw top-down BGRA bytes that Media
Foundation consumes, with no image encode and no bitmap allocation per frame.
Both shapes share one D3D11 staging copy so the two backends can never disagree
about geometry or orientation.

Both channels hold two frames and drop the oldest. A slow consumer therefore
loses stale animation instead of accumulating latency or memory, and the number
of frames the channel had to supersede is observable (`PublishedRawFrames`
minus `ConsumedRawFrames`) and reported as dropped frames.

The private render window is still converted to a non-activating tool window
before capture starts (`ConfigurePrivateRenderWindow`), so the requirement that
it never appears in the taskbar or Alt+Tab is unchanged from v0.3.

## 3. Encoder (`MediaFoundationH264Encoder`, `MediaFoundationInterop`)

Media Foundation is driven by raw vtable invocation rather than COM interop
proxies. Media Foundation objects are free-threaded but are not registered with a
proxy/stub, so a runtime COM wrapper only works from the apartment that created
it; a call from a thread-pool continuation fails with `E_NOINTERFACE`. Every call
is therefore a direct vtable call on one multi-threaded apartment thread, which
is the same technique the existing D3D11 capture code already uses. All GUIDs and
vtable indices are taken from the Windows SDK headers.

The container is written to a managed `IMFByteStream` implementation instead of a
file. No temporary media reaches the disk, nothing has to be watched for growth,
and a slow consumer throttles capture through the byte stream rather than growing
a queue. `IMFByteStream::BeginWrite` signals its completion callback; a stream
that writes immediately but never signals completion makes the MPEG-4 sink wait
forever inside `WriteSample`, which is exactly the failure this implementation
hit and fixed.

`Mp4ChunkAssembler` reassembles whatever Media Foundation writes into complete
top-level boxes and groups them into the two units Media Source Extensions
accepts: one initialisation segment (everything up to and including `moov`) and a
series of `moof`+`mdat` media fragments. The splitter is driven purely by the
big-endian box headers because Media Foundation does not promise that one
`Write` call equals one box. It fails closed on invalid, unbounded or oversized
boxes, and a failed assembler never returns further data.

The encoder reports whether Media Foundation actually instantiated an
asynchronous (hardware) MFT, reading `MF_TRANSFORM_ASYNC` from the encoder's own
attributes, so a silent software fallback is labeled `software` instead of being
reported as GPU acceleration. The exact Media Source codec string is read from
the `avcC` decoder configuration the encoder produced, never guessed.

### 3.1 The declared frame rate is authoritative, so it must be measured

Media Foundation does **not** take per-sample durations at face value: it
resamples the media timeline to the frame rate declared on the media type. This
was established by experiment, not assumption. Stamping each sample with the
interval that really elapsed (220 ms) while declaring 60 FPS produced 517 coded
frames from 45 submissions — exactly 8.58 s x 60 FPS. Two consequences follow,
and both are now enforced in code:

1. **The declared rate is chosen by measurement.** `GpuMediaPipeline` measures the
   live capture cadence before creating the encoder, deliberately discarding the
   first 500 ms because a Scene that has just started is still compiling shaders
   and would be under-reported. `GpuStreamStatusLabel.AlignFrameRate` then declares
   85 % of the measured rate, capped by what the user asked for. The margin is
   deliberate: the source rate varies over a session, and when the declaration is
   wrong, dropping frames is cheaper and smoother than repeating them.
2. **The claimed cadence comes from the source, never from the coded count.**
   Because the timeline is resampled, the coded frame count can legitimately
   exceed the number of distinct frames the Scene produced. The status therefore
   follows `SubmittedFrames` per second — frames that really came from the capture
   surface — and the `coded / submitted` ratio is reported as its own diagnostic so
   duplication is visible instead of flattering. The live smoke test fails the run
   if the status ever claims the 60 FPS target while the source delivered fewer
   than 55 distinct frames per second.

## 4. Transport

Encoded fragments are delivered over the CDP session the controller already uses
to install and control the wallpaper layer. No listening socket, no URL
capability token and no loopback server exist in this build: `connect-src` on the
Codex app page excludes loopback, so the network variants are unreachable and
ADR-007 records the measurements. Because networking is not used, there is
nothing to authenticate and nothing to close beyond the session itself.

The transport is deliberately batched. Media Foundation emits one fragment per
frame, so a message per fragment would reproduce the per-frame control traffic
Issue #2 asks the v0.4 path to remove; a batch carries four fragments, or 384 KiB,
or waits at most 60 ms. The initialisation segment is never held back, because
the page cannot create its media buffer until it arrives.

Delivery is acknowledged by the page. `presented`, `appended`, `busy`, `stale`,
`rejected` and `decode-failed` are distinguished; only `busy` is retried, because
the page rejects a `busy` batch without consuming its sequence numbers, which
makes resending it idempotent. Every other refusal is terminal and is reported
instead of being hidden behind a retry loop.

## 5. Decoder and presenter (renderer)

`companion/Runtime/gpu-surface.js` (bundled into the injected runtime) owns one
persistent `<video>` element and one `MediaSource`. It never creates a second
element, never rebuilds the `SourceBuffer` for a transient error, and never
touches the element's source after construction. It waits for `sourceopen`,
creates the `SourceBuffer` with the codec string the encoder reported, honours
`sourceBuffer.updating`, keeps the buffered window at or below two seconds,
re-seeks to the live edge when it drifts, and retries a `QuotaExceededError`
once after removing the oldest range that does not contain `currentTime`.

`presented` is returned only when a frame is genuinely on screen: a
`requestVideoFrameCallback` fired after that append, or a presentation confirmed
within the last two seconds. `readyState` alone is never treated as proof, which
is what stops the controller from reporting a wallpaper switch the user has not
seen.

Nothing clears, blanks, hides or detaches the surface on an append error, a
stall, or a fragment from a foreign stream. Retaining the last decoded frame is
the entire point of the component.

## 6. Session ownership and transactional switching

`WallpaperEngineCaptureSession` owns one immutable stream identity
(`GpuMediaPipeline.StreamId`, a 32-hex token). Every fragment carries it, and the
page rejects any fragment whose identity is not the active one.

Applying a wallpaper is transactional. The initial frame is uploaded and painted
first, so the user sees the new wallpaper immediately. The GPU surface is then
created *above* the current background while still empty, and the previous
wallpaper is retired only after the replacement has presented a frame of its own.
A replacement that never presents therefore leaves the current frame visible, and
a stream that never presented leaves the previous decoder alive rather than
replacing it with nothing.

Wallpaper changes therefore cannot show an old wallpaper's frame after promotion:
the replaced surface is disposed in the same step that promotes the new one, and
late fragments from the old identity are rejected as `stale`.

## 7. Fallback ladder

| Condition | Result |
| --- | --- |
| GPU pipeline starts, page accepts the surface | `GPU dynamic — 60 FPS target` |
| 30 FPS mode requested for constrained hardware or higher resolution | `GPU dynamic — 30 FPS fallback` |
| GPU pipeline or page surface refused at apply time | rebuilt on the compatibility backend, labeled `reduced-frame-rate JPEG compatibility`, with the refusal reason shown |
| A `busy` transport answer | bounded retry with backoff, status `recovering` |
| Terminal transport refusal or capture/encoder failure | GPU loop stops, the last confirmed good frame stays on screen, status `unsupported or failed` with the reason |
| No native renderer available at all | unchanged v0.3 static/preview fallback |

A Stream restart is only published through the status surface when it is real:
`GpuStreamStatusLabel.Decide` refuses to report a GPU state unless the GPU path is
actually active, and reports `degraded` when a GPU mode cannot hold 28 presented
frames per second.

## 8. Diagnostics

`GpuStreamDiagnostics` records capture resolution, requested/captured/coded
cadence, captured frames, the frames the source published and the frames the
bounded channel had to supersede, rejected and encoder-dropped frames, encoded
bytes, encoded/delivered/presented/stale/rejected fragments, maximum queue depth,
median and p95 encode-to-present latency, encoder and decoder mode, recovery count
and longest recovery, the average per-frame wait and encode hand-off cost, the
current stream identity and the last successful presentation time. Latency samples
live in a fixed 256-entry reservoir, so a long-running wallpaper cannot grow the
diagnostic footprint without bound.

Two accounting rules exist because getting them wrong produces plausible lies.
Published and superseded frames are **gauges**, not counters: the capture channel
supersedes older frames, so the number left behind is a difference, and
accumulating that difference on every read reported hundreds of phantom drops
before it was fixed. Presented cadence counts **frames**, not transport messages,
because one batched message carries several Media Source units.

The record contains no captured pixels, no Workshop or project paths, no user
state and no credentials; the unit tests assert that its rendered form carries no
drive path.

## 9. Cleanup

`Restore` disposes the GPU surface in the page, stops the encoder, releases the
capture source and closes the private Wallpaper Engine window. The static cleanup
script used by `--restore` and `CleanupAllAsync` enumerates and disposes the GPU
surface as well, and cleanup verification fails if the injected globals survive.

## 10. Deliberate deviations and known limitations

Recorded honestly; see the acceptance report for the same list with measurements.

1. **CDP still carries encoded video.** Issue #2 asks that CDP not carry normal
   video frames. The page cannot reach a loopback endpoint because of its own
   content security policy, so the alternative was relaunching Codex with web
   security disabled or reloading the app page. Both are worse for the product.
   The deviation is batched, bounded, and reversible behind the transport seam;
   ADR-007 records the evidence and the escape route.
2. **The capture source is the cadence ceiling, and it is Wallpaper Engine's own
   limit.** Three measurements establish this. A source-only capture that performs
   no copy and no map measured 24.9 frames per second against 24.8 with the full
   readback, with every published frame consumed, so the consumer costs the source
   nothing. The rate is independent of the render scale (24.7 / 25.0 / 25.0 at 0.5
   / 0.75 / 1.0), so it is not pixel throughput. And Wallpaper Engine's own
   configuration carries a global frame rate limit — `general.user.fps`, measured
   as 25 on this machine — which the observed rates sit exactly at or below. The
   product therefore reports the measured source cadence and names that setting as
   the remedy when it explains the shortfall, instead of advising a lower render
   scale, which the measurements show does not help.
3. **Media Foundation resamples to the declared rate.** See 3.1. This is why the
   declared rate is measured rather than assumed, and why the claimed cadence is
   taken from source frames rather than coded frames.
4. **Mid-session GPU failure does not rebuild the surface.** A terminal failure
   keeps the last good frame and reports `unsupported or failed`; the next apply
   selects the compatibility backend. Rebuilding the page surface mid-session
   needs a second `BeginGpuStream` handshake and is the main follow-up. A measured
   consequence is that a rate measured before the source has settled is used for
   the session's lifetime, because changing it means rebuilding the stream.
5. **Pointer forwarding is unchanged and compatibility-only.** It never blocks
   playback, and no general mouse-interaction reproduction was implemented.

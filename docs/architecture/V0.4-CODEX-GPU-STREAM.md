# v0.4 Codex GPU stream architecture

## Product path

For a supported Wallpaper Engine Scene, the controller now uses one owned
session from rendering through presentation:

1. Wallpaper Engine renders the original Scene through its documented
   `playInWindow` interface.
2. The private render window is marked `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`
   with `WS_EX_APPWINDOW` removed. It stays composed off-screen, is not
   minimized, and remains capturable without appearing in the taskbar or
   Alt+Tab.
3. Windows Graphics Capture supplies D3D11-backed frames. The current encoder
   adapter performs a bounded CPU readback and BGRA-to-NV12 conversion before
   submitting frames to a Windows Media Foundation hardware H.264 transform.
4. A bounded publisher coalesces compressed Annex-B H.264 frames. Obsolete
   work cannot grow without limit.
5. Codex uses one persistent canvas and one persistent WebCodecs
   `VideoDecoder`, preferring hardware decoding and compositor presentation.

The controller waits for a decoded frame before reporting Apply as successful.
Every callback and browser helper carries an immutable random stream identity;
a late frame from a replaced stream is rejected. Switching or Restore cancels
the producer, closes the encoder/publisher/decoder, asks Wallpaper Engine to
close the named render window, and verifies that the window was released.

## Transport decision and Codex constraint

The intended production transport was a token-scoped loopback WebSocket.
Capability testing in the current Codex build showed that its app Content
Security Policy rejects an additional `ws://127.0.0.1:<port>` connection. The
controller does not weaken, patch, or bypass that policy.

The working v0.4 prototype therefore sends compressed H.264 access units in
bounded, coalesced batches over the already-authorized CDP control connection.
This removes per-frame JPEG encoding, greatly reduces the number of CDP calls,
and retains hardware encode/decode, but Base64 remains inside the JSON batch.
Consequently this branch is not yet a full pass of the specification's
“normal video frames never travel through CDP” hard gate. The loopback binary
server remains capability-gated for a future Codex environment that permits
it; no listener survives session cleanup.

## Reliability and recovery

- Capture and publisher queues are bounded; backpressure cannot accumulate an
  unbounded delayed stream.
- Empty and implausibly uniform capture frames are rejected. The browser keeps
  the last confirmed frame instead of replacing it with black or gray.
- A replacement is not reported as active until its first H.264 frame has been
  decoded and drawn.
- The GUI monitors the exact current session task. An unexpected stop triggers
  at most two recovery attempts with 1-second and 3-second backoff. User
  switching, Restore, cancellation, or a newer session prevents that retry.
- After both attempts fail, recovery stops and the status surface retains the
  last frame and asks for a manual retry. There is no infinite restart loop.
- Mouse-interaction reproduction is intentionally disabled on the H.264 path;
  it no longer produces high-frequency CDP polling or destabilizes playback.

## Status and diagnostics

The normal status distinguishes the hardware H.264 path from the loopback and
JPEG compatibility paths. It also reports when Wallpaper Engine's global Scene
FPS setting is lower than the requested 30/60 FPS target.

Doctor reports the requested Scene FPS, detected Wallpaper Engine FPS limit,
available Windows hardware H.264 encoders, and any encoder-probe error. Active
stream diagnostics include captured/encoded/received/presented/dropped counts,
publisher batches and bytes, decoder queue depth, current stream identity,
last successful presentation, cumulative recovery attempts, capture/encode
time, mode, and transport error.

No captured pixels, Workshop assets, credentials, or private local paths are
written to these diagnostics.

## Compatibility and fallback

If hardware encoder initialization or WebCodecs presentation fails, the
controller releases the failed render session and creates a clean replacement
before entering the explicitly labeled compatibility path. Static images,
ordinary videos, the built-in safe Scene renderer, search, rename, collections,
filters, fit/focus/color controls, queued Apply, startup restore, and explicit
Restore retain their v0.3 behavior.

## Dependencies and licensing

`Vortice.MediaFoundation` 3.6.2 (MIT) provides managed access to the Windows
Media Foundation API. It does not bundle a codec; the selected H.264 encoder is
provided by Windows/GPU drivers. Origin and license links are recorded in
`THIRD_PARTY_NOTICES.md` and included in the portable package.

## Known limitations and next convergence candidates

1. Replace the bounded CDP batch publisher when Codex exposes an authorized
   local media transport or native background-texture API.
2. Accept D3D11 textures directly in the Media Foundation encoder to remove the
   current CPU readback and BGRA-to-NV12 conversion.
3. Complete the shared 60 FPS, 10-minute and 50-switch gates with Wallpaper
   Engine globally configured to 60 FPS.
4. Add synthetic fault injection for capture, encoder, transport and presenter
   failures so every recovery branch is deterministic in CI.

Rollback is safe: Restore removes the injected browser layer and closes all
owned session resources. The previous stable implementation remains available
from `main` and the preserved v0.3 branches.
